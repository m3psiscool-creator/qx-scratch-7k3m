# FN Game Analyzer

Hosted site that predicts the points needed for any rank (1-10,000) in Fortnite FNCS, Cash Cup and Skin Cup (ShopCup) windows, live and before they start. Production: https://fn-game-analyzer.vercel.app (Vercel, project `fn-game-analyzer`, team james-projects-996f2671, Hobby plan). Repo: github.com/m3psiscool-creator/fn-game-analyzer.

## User preferences
- Short answers; list every step; critique own answer; ask for missing info rather than guess.
- User is on Windows (PowerShell). Use the full python path (`%LOCALAPPDATA%\Programs\Python\Python312\python.exe`) in non-fresh shells.
- User does NOT want to run commands on their computer: everything runs on Vercel.

## Architecture
- `index.py` FastAPI entrypoint. Serves `web/` (index.html, style.css, lib.js = helpers + chart theme, strategy.js = Strategy tab, app.js = pages + router; hash-routed SPA, Chart.js from cdnjs) and `/api/*`. New static files need a route in index.py.
- `fngameanalyzer/`: `config` (regions, lobby sizes, DEEP_RANKS), `auth` (rolling Epic refresh token in DB, lock), `epic_api` (events + leaderboards, parallel pages, deep thresholds), `classify` (event class), `rules` (scoring rules, rescoring), `storage` (sqlite local) / `storage_pg` (Neon Postgres, chosen by POSTGRES_URL), `collector` (tick), `model`/`sim` (prediction), `service`/`insights` (API logic), `strategy` (scoring values, finisher profiles, pace curves, safety margin, rank ladder; feeds the Strategy tab via /api/scoring, /profile, /pace, /safety, /ladder).
- Tick: `/api/tick` (header `x-admin-key` or Vercel cron bearer). cron-job.org calls it every minute; one pass takes <25s (Hobby cron is daily only). Each pass: sync event list (every 10 min, all regions), snapshot live windows (until end + 25 min, because games started before the end still count), store finals (backfill newest first), deep thresholds backfill, stored predictions, player-name backfill.
- Storage per window: top-1000 points/games/per-game sessions (placement, elims, win, end time)/players, plus points at ranks 1000,1500..10000 (`deep`). Snapshots also write compact `series`. Full snapshots of finished windows are pruned after 3 days.

## Model
- Events are classified (`classify.py`): reload|br, zb, solo|duo|trio|squads, mobile. History is only used within the same class (checkbox `approx` allows nearby classes explicitly), and the same format (game count + scoring). Same-region events come first and carry the most weight; other regions of the same gamemode and format are added only when the region has fewer than `model.MIN_SAME_REGION` (4) previous events (`model.comparable`, `strategy.peers`, strategy `_refs`).
- Live: player-by-player simulation (`sim.py`) using comparable players at the same moment in same-class past events (games played, points/game, pace scaling), with back-test bias correction. Ranks >700 scale from rank 500; ranks never predicted below current.
- No history for a class = explicit "no history" message.

## Strategy layer (added Oct 2026)
- `strategy.py` feeds the Strategy tab: `/api/scoring`, `/profile` (finisher bands, per-game sequences, styles), `/pace`, `/safety`, `/ladder`, `/tempo` (minutes per game by placement from consecutive game end times; a stored game time is the player's elimination time); `me.py` looks a player up by Epic name on the public leaderboard (`/api/me`, `/api/account`); `service.sessions` (`/api/sessions`) lists the rounds/editions of an event in a region; `/api/calendar.ics`, `/api/feedback` (owner reads with the admin key), `/api/health` (banner).
- Front end: `lib.js` (helpers, Chart.js theme, zoom/click wiring), `strategy.js` (recommendation, plan, simulation, coach notes), `app.js` (pages, router, account chip, banner). Charts use `mk()`; animations are off on purpose (Chart.js errors when a click redraws a chart).
- Timing facts that drive the plan: games left = format games minus games played; games that fit = time left / minutes per game at your placement (a game may start right before the window closes). Finishers' points fall with game number, so checkpoints and the simulation follow real sequences, not an even split.
- Tests: `python -m unittest discover -s tests`.

## Operations lessons
- **Never run local code that uses the production Epic login** (`auth.Session`, `/api/me`, `/api/account`, the collector). The refresh token rotates on every use; the live login died on Oct 14 2026 while local tests were also using it (cause not proven). Local test servers must stub `auth.Session` (see how `serve.py` in a scratch folder does it) and intercept `/api/me` in browser tests. Re-login (Status page) is the only fix and needs the owner's Epic authorization code.
- `auth_bad` in kv marks a refused login; `auth.bearer` then waits 10 minutes before calling Epic again. The site shows a banner when the collector has not run for 15 minutes or the login is invalid.
- Do not read other players' Epic data by account id: Epic returns 403 for anything but your own account; the public leaderboard (`Epic.find_entry`) is the only way.

## Roadmap ideas not built
- Real gameplay telemetry (landing spots, rotations, fights): Osirion's public API or replay parsing. Needs a terms check first; plan-aware drop advice ("which drop fits your target rank, time and style") is the differentiator.
- Clock-time advice ("when to queue") was tested and rejected: later games score more only because deep runs end later, so survival and clock time cannot be separated.

## Dropspots (landing data)
- Tab `#/drops[/window]` (`web/drops.js`, `drops.py`, `/api/drops/*`): heatmaps of where teams landed (qualified = final rank within the top N, versus everyone), a game filter, drawn areas (box, freehand, named spot) with the stats of the teams that landed there, and a comparison table of named spots. It also states which playlist/map an event uses (Epic's event data only gives the playlist id).
- **The leaderboard has no landing data; the replays do.** Epic keeps a server replay of every tournament match for about 1-2 weeks, keyed by the `sessionId` that each leaderboard entry lists per game (same id Osirion/Fortnite Tracker show as match id). Rows go in with `POST /api/admin/drops` (format in `docs/dropspots-data.md`); tables `drops` and `drop_maps`.
- **Replay pipeline (no paid service):** `GET /api/admin/matches?window=` lists every session of a window with its teams, rank, game number, placement, elims, points (`replays.matches`); `GET /api/admin/replay?session=&max_ms=` returns the file list and 15-minute signed links (`replays.links`; metadata at `/api/v1/data/fnreplaysmetadata/public/<id>.json`, links by POSTing `{files:[...]}` to `/api/v1/access/fnreplays/public/<id>/`; the site's own login works). `worker/replay.mjs` downloads the header and only the first data chunks (landings happen in the first minutes; ~8 MB instead of 43) and assembles a `.replay`; `worker/landings` (C#, net10, references Shiqan/FortniteReplayDecompressor, GPL-3.0, pinned commit 76f74c1, pure C# Oodle) prints each player's landing = first moment after leaving the bus with vertical velocity exactly 0, plus a ground trail; `worker/run.mjs <window>` ties it together (samples matches: half the ones with most qualifiers, half random; teams matched to the leaderboard by account ids; north-up map: u = Y, v = -X; posts rows, a background map drawn from player movement `map.base`, and `sessions_done` so reruns skip finished matches). `.github/workflows/drops.yml` runs it every 3 hours on GitHub Actions and needs the repo secret `ADMIN_KEY`.
- The map background is drawn from where players moved (no outside image, no copyright question); bounds default to +-55000 world units (`MAP_BOUNDS`). Named spots are not available (Epic ships no POI table in the replay): only drawn areas.
- **Evaluation cups** (Epic's `tournamentType` WorkshopCup, "Performance Evaluation Trios", family `WORKSHOP`, label "Evaluation cup") are collected like the other types (`config.TOURNAMENT_TYPES`). They are Battle Royale trios, so the worker uses world bounds +-131072 for `game_type == br` (Reload maps +-55000). Admin helpers: `/api/admin/event_scan?q=` lists every event Epic offers (also untracked types), `/api/admin/sync_test?region=` shows what the window parser returns.
- **Never a map made from player movement** (owner's rule): the tab shows a real image of the map or a plain grid with "No picture of this map is available yet". Real images come from the Fortnite Wiki overview images (game renders; all Reload maps except one) and fortnite-api.com for the Battle Royale island. The Victory Cup map (codename `PiperBoot`) comes straight from the installed game (C:\Program Files\Epic Games\Fortnite): `tools/mapfit/mapdump` (CUE4Parse, clone in %TEMP%\cue4) mounts the paks with the AES keys from fortnite-api.com/v2/aes and the Fortnite `.usmap` that FModel itself downloads (`https://uedb.dev/svc/api/v1/fortnite/mappings`, file on data.uedb.dev); no FModel and no running game needed. Minimap material `BlastBerryMapUI/Minimap/MI_MiniMap_<codename>_MapBase` points at the texture (`Discovered_PiperBoot`, 2048x2048); fitted by likelihood (`tools/mapfit/fit_likelihood.py`): turned 180 degrees, L=1.56 (same scale as Nitemare), 94% of landings on land in two separate windows. New map = find its `MI_MiniMap_*` the same way.
- **Raw map textures and automatic fit** (`drops._RAW`, `_auto_fit`, `web/maps/raw-*.jpg` + masks): all Reload maps in the game files (BlastBerry, DashBerry, ForbiddenBlastBerry, MatchMist, PunchBerry, RopeSmile, TigerRanch, TimberStake; `Discovered_<codename>`, BlastBerry is `Capture_Iteration_Discovered_BlastBerry`) ship as raw pictures and the page (`warp` in `web/drops.js`) turns them into the 0-1 frame with `fit` = {k quarter turns counter-clockwise, L = 1.55 frames wide, cx, cy}. The turn differs per map (Nitemare 1, BlastBerry 0, Victory 2), so a map without a measured fit is fitted from real landings (4 turns x centre, mean log-likelihood of landings spread over land, accepted only with a clear gap to the next turn and enough land hits, then stored in kv `mapfit:<codename>`) and is hidden until then. `picture_check` allows for small samples (share + 1.64 standard errors must reach the map's bar). JumpBear (Mobile cups) has no texture in the installed game yet; DashBerry's replays were already gone (retention is about 4 weeks, not 1-2), so it shows once a tournament on it has data. Maps used by tournaments so far: BR island, SourSpawn, PiperBoot, BlastBerry, DashBerry, JumpBear.
- **Map picture** (`drops.MAPS`, `web/maps/`): registered per playlist codename (`SourSpawn` = Nitemare Island, found by fitting wiki overview images to the landings and by names inside the replay, see `tools/mapfit/`). The picture is rotated/scaled into the site's 0-1 frame and ships with a land/water outline (`*.mask.json`); `drops.picture_check` tests the real landings against it and hides the picture when under 93% are on land (`map_check` in `/api/drops/info`). A new codename has no picture until someone identifies it (draws the background from player movement meanwhile).
- **Chests and loot** (`/api/drops/loot`, `/areas`, `_sites`): the replay has no chest objects (UEFN maps), but a chest opened by a player spits out 5+ pickups at one spot within 0.6 s. The landing tool (`Spy` in `worker/landings/Program.cs`) finds those bursts after 40 s of replay time, **removes player-death drops** (burst within 600 uu and 4 s of a player's DeathLocation/DeathTime, using the game-clock offset taken from PlayerPawn timestamps) and anything over 9 items; the worker counts per 360x360 map cell the matches that had a burst and the server (kv `chests:<codename>`, shared by every event on that map) turns peaks seen in at least 5% of matches into chest sites. **Lootage rate** = share of matches in which that chest was opened in the first minutes (about 3 min of game, the downloaded part). Areas = greedy clusters of sites (radius 0.055) with chests, lootage, average players per game (landings share x teams per match x team size, counted from every team in the replay, not only the leaderboard), loot score = chests / (players + 1), chests per player and chests still free. Needs 20 processed matches of a map.
- **Exact container positions (replaces the loot-burst guess, owner: "chests are not accurate at all"):** every placed container (chest, rare chest, ammo box, produce box, cash register, fishing barrel) has a stable unique name in the replay (`Tiered_Chest_Sunflower_C_UAID_...`) and its export group has `bAlreadySearched` and `SearchingPawn` (the pawn that is searching). `worker/landings/Containers.cs` registers those groups (the tool's assembly is named `LandingsReplayReader` because the parser only scans assemblies with `ReplayReader` in the name), `Spy` remembers every pawn's last position and, at the first search of a container, records the searcher's position = the container's position. The same chest gives the same spot in different matches within about 1.3 m (median; 90% within 3.7 m). `worker/run.mjs` posts them (`POST /api/admin/containers`, matches counted once via kv `ctn:<map key>` `done`), the server keeps per name the number of searches and up to 15 positions (median = place) and `drops._container_sites` turns them into sites with a class (`_kind`) and a rate = searches / matches. Nitemare: 479 chests + 16 rare + 601 ammo boxes (fortnite.gg lists about 470 chests). The old burst/cell method (`_sites` fallback) is only used below 20 container matches. `/api/drops/loot?cls=all` returns every class. No replay contains slurp barrels / slurp trucks as searchable containers (fortnite.gg lists them: Nitemare, BR), so there are no slurp layers. fortnite.gg itself blocks bots (Cloudflare) and draws its markers on a canvas: it is only a visual reference, read through the owner's Chrome extension.
- **Map catalog** (`drops.CATALOG`, `/api/maps`, `web/map.js`): every map fortnite.gg lists by its in-game name (BR, OG, Blitz: Venture / Asteria Awakened / Stranger Things / Starfall Island / Stark Island; Reload: Venture = BlastBerry, Oasis = PunchBerry, Slurp Rush = TigerRanch, Squid Grounds = TimberStake, Surf City V1 = PiperBoot, Nitemare Island = SourSpawn, Elite Stronghold = MatchMist (its FrontEndMapMarkers name ELITE EXPERIMENTS / TOP TIER TRAINING), Springfield = DashBerry, Blitz Venture = ForbiddenBlastBerry). RopeSmile (snow + lava) is not matched to a fortnite.gg name. Pictures: game textures where the install has them (raw-*.jpg), wiki icons for the Blitz maps (icon-*.png), the wiki map for OG; Asteria Awakened has none. A map without replay data shows its picture only.
- **Rotations tab** (`#/rotations[/session]`, `web/rotations.js`, `tracks.py`, `worker/tracks.mjs`): `TRACKS=1 LandingsReplayReader.dll <replay>` prints every player's path (a sample about every 4 s, world coordinates + height/100), deaths and the storm circles (SafeZoneIndicator: next circle and shrink start/finish, world clock) of a FULL replay. `tracks.mjs <window> [--limit N] [--top N]` picks the matches with the most qualifying teams, converts to the stored frame (integers of 1/10000) and posts `/api/admin/tracks`; the server keeps one zlib row per match (`tracks`, about 50-130 KB) and one row per player (`track_players`, indexed by account). `/api/tracks/player?account=`, `/api/tracks/game?session=` (paths turned like the map, storm, teams with names and event rank), `/api/tracks/recent`. The page: search a player, open a game, play/scrub the match, follow a team (a table shows where it was when each zone started closing and when it closed, and whether it was outside). Samples outside the map are the pre-game island and are never drawn. The scheduled job reads 4 full replays per window. Next step (owner): record the zone the user gives and suggest rotates from where qualified teams stood at each zone.
- **Dropspots grid** (`web/drops.js`): the 10x10 grid A1-J10 is drawn on the map (ticker "Grid"), clicking a square selects it (mode "Grid square"; drag pans), and the area panel lists the best teams that landed there ranked by final event rank (`drops.area` -> `teams`). The "Named spots" ticker is gone.
- **Frame, rotation and map names (owner's calls):** every map is shown the way the game draws it (north up, like the in-game map and fortnite.gg). The loaders store landings in their own frame (u east, v south); the site turns it a whole number of quarter turns clockwise per map (`_turn`, `MAPS[code]['rot']`: Nitemare 1, Surf City V1 2, Venture 0, BR 1; a raw texture without one gets the turn its landing fit finds, kv `maprot:<code>`), applied in `_arrays` and `_sites` (chest cells via `np.rot90(C, -rot)`). Pictures: Nitemare, Surf City V1 (PiperBoot) and Venture (BlastBerry) are the in-game map textures (`raw-*.jpg`, same art as fortnite.gg) with `fit` measured on landings and then refined on chest sites sitting on building pixels (`tools/mapfit/align_chests*.py`): width 1.58-1.61 frames for every Reload map. BR keeps the fortnite-api picture (rot 1). Names: SourSpawn = Nitemare Island, BlastBerry = Venture, PiperBoot = Surf City (new) (the tournament island: no mountain, rebuilt harbour; the Dec 2025 map in the game files is kept as catalog entry Surf City V1). Chest sites in the sea of the map's own outline are dropped (`_on_land_only`). Chests are drawn as chest icons (`drawChest` in lib.js) tinted by early lootage.
- **Map tab** (`#/map[/window]`, `web/map.js`, `/api/maps` = `drops.maps()`): one entry per chest atlas with sites; canvas map with pan/zoom/hover, every chest site plotted and coloured by early lootage, a lootage filter, grid and landing-heat layers, most/least contested lists. Picture and sites come from `/api/drops/info` and `/api/drops/loot` of the best window of that map (raw textures are warped client-side with `warp`).
- **One prediction everywhere:** `service._share` saves every calculator result for the tracked ranks (PRED_RANKS, advance ranks, goal) into the predictions table, so the home page (reads the latest stored prediction) shows the same number as the rank calculator; the bubble headline "Expected to end near" is the same `run_predict` result (the per-player table is still the bubble simulation).
- Teams not on the stored leaderboard (rank beyond 10,000) are still loaded: game number 0 (only in "All games"), rank 0, points from the replay's elims.
- Predictions: `service._run_predict` accepts any top 1-10,000; ranks 701-1000 read the stored top-1000 boards of same-format events, ranks above 1000 interpolate the stored thresholds; a field-size check says plainly when a rank is outside what events of that format had (small finals have 17-20 teams).
- **Never refuse a prediction (owner's rule):** `service.run_predict` tries past events of the same gamemode and format first, then the same gamemode, then similar gamemodes (`model._ctx.approx`, no checkbox any more; the `approx` query parameter is ignored) and flags `similar_modes`; a rank deeper than the field returns the last-place estimate with a `note` (`_Beyond`); a rank over 10,000 is clamped; the bubble table clamps goals to 700 and widens the same way; strategy pace uses the deepest ranked curve. Only with no finished history anywhere does it return an error. Never word a message as "rank X is not tracked/stored".
- Operations: the replay endpoints use the production Epic login only for small requests (never run the collector or `auth.Session` locally; the worker only talks to the site). Auto-mode classifier on the dev machine often blocks these commands; they succeed right after the user says "run".
- **View box (map pictures whole, owner: "images are cut off"):** the game texture is about 1.6 frames wide, so the old 0-1 frame cut the island. `drops._view(code)` = the square (x0, y0, s) of the turned frame that holds all land of the map's mask (+6%); `_arrays`, `_sites` (wrapper over `_sites_turned`), `map_info` (fit, pois) and `tracks.game` express everything in that square, so 0-1 on the site is the whole island and the grid A1-J10 covers it. Landings/containers are stored in the loaders frame and may lie in -0.7..1.7 (`WIDE`); the worker (`run.mjs`) and `ingest`/`add_containers` no longer drop them. Container counts are kv `ctn2:<map>` (full frame); `_container_sites` keeps the older `ctn:` items (more matches, clipped) and adds items only `ctn2` has. The ctn2 atlas fills as the 3-hourly job reads matches (needs the Epic login).
- **Validation against fortnite.gg (owner's reference for chests):** `tools/mapfit/validate_fortnitegg_*.py`: screenshots of fortnite.gg's map (owner's Chrome) are registered to the game texture with SIFT, chest icons found by template matching, and compared with our sites (ICP gives offset/scale). Nitemare was 4 m off, Surf City V1 about 10 m; both fits were corrected (`_RAW`); after that residual median 2-2.6 m, and in Haunted Hamlet 48 of ours vs 49 on fortnite.gg. BR cannot be registered automatically (different artwork); Venture has no chest containers in its replays (names unknown).

- **Surf City (new) vs V1 (owner: "add the NEW Surf City"):** the PiperBoot texture in the game install (`raw-surfcity.jpg`, = wiki "Surf City - Island") has a mountain peninsula in the north-east that the tournaments never use (2 of 4,204 landings there; chests in the canal water). The Fortnite Wiki render `Surf_City_(v42.20)_-_Island_-_Fortnite_Reload.png` (Aug 17 2026, same coordinate frame as the texture: SIFT gives 2,068 inliers, scale 0.625) fits: 99.6% of landings on its land and chests on its harbour buildings. It is `web/maps/raw-surfcity2.jpg` (2048 px, mask from `tools/mapfit/make_mask_sea.py`) and the picture of PiperBoot; the old one is catalog key `SurfCityV1` (picture only). The Remix (Sept 24 2026: Heatwave Harbor, Squibbly Shores) is not in the wiki or in the June game install; if the data ever shows it, update the install (Epic launcher) and rerun `tools/mapfit/mapdump`.
- **BR picture fit (owner: "BR is completely inaccurate"):** the fortnite-api picture is not the 262,144-unit replay frame: fit {L 1.07, cx .5225, cy .490} (in `MAPS["BR"]`, now a `raw` picture warped client-side like the Reload maps), found by maximising chest sites on land and on grey buildings (both peak there) and checked on the POI world positions from fortnite-api.com/v1/map (Pac-Man/Blinky/Pinky Island within about 80 m). BR chest sites seen in under 10% of matches are hidden by default (Map tab slider, Dropspots layer): BR chests spawn at random places.
- **Accuracy (owner's spec):** `insights.accuracy` returns buckets (Start, 25, 50, 75, 90% of the event: average/median error, bias, in-range) and per event/rank the predictions over time vs the real cutoff; the page has chart A (error and bias by moment) and chart B (pick tournament + rank: predicted low/likely/safe against the real end). Every finished tournament is predicted as of its start from earlier events only (`service.prestart`, `collector.backfill_prestart`, kv `prest2:<window>`, a few per tick; `/api/admin/score?seconds=200` runs a long batch, `/api/admin/prestart?window=` shows one), every live window is predicted by `store_predictions` (all windows per pass, oldest first).

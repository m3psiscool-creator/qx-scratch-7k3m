# FN Game Analyzer

Hosted site that predicts the points needed for any rank (1-10,000) in Fortnite FNCS, Cash Cup and Skin Cup (ShopCup) windows, live and before they start. Production: https://fn-game-analyzer.vercel.app (Vercel, project `fn-game-analyzer`, team james-projects-996f2671, Hobby plan). Repo: github.com/m3psiscool-creator/fn-game-analyzer.

## User preferences
- Short answers; list every step; critique own answer; ask for missing info rather than guess.
- User is on Windows (PowerShell). Use the full python path (`%LOCALAPPDATA%\Programs\Python\Python312\python.exe`) in non-fresh shells.
- User does NOT want to run commands on their computer: everything runs on Vercel.

## Architecture
- `index.py` FastAPI entrypoint. Serves `web/` (index.html, style.css, lib.js = helpers + chart theme, strategy.js = Strategy tab, app.js = pages + router; hash-routed SPA, Chart.js from cdnjs) and `/api/*`. New static files need a route in index.py.
- `fngameanalyzer/`: `config` (regions, lobby sizes, DEEP_RANKS), `auth` (rolling Epic refresh token in DB, lock), `epic_api` (events + leaderboards, parallel pages, deep thresholds), `classify` (event class), `rules` (scoring rules, rescoring), `storage` (sqlite local) / `storage_pg` (Neon Postgres, chosen by POSTGRES_URL), `collector` (tick), `model`/`sim` (prediction), `service`/`insights` (API logic), `strategy` (scoring values, finisher profiles, pace curves, safety margin, rank ladder; feeds the Strategy tab via /api/scoring, /profile, /pace, /safety, /ladder).
- Tick: `/api/tick` (header `x-admin-key` or Vercel cron bearer). cron-job.org calls it every minute; one pass takes <25s (Hobby cron is daily only). Each pass: sync event list (every 10 min, all regions), snapshot live windows (until end + 25 min, because games started before the end still count), store finals (backfill newest first), deep thresholds backfill, stored predictions, player-name backfill.
- Storage per window: top-1000 points/games/per-game sessions (placement, elims, win, end time)/players, plus points at ranks 1000,1500..10000 (`deep`). Snapshots also write compact `series`. Full snapshots of finished windows are pruned after 3 days.

## Model
- Events are classified (`classify.py`): reload|br, zb, solo|duo|trio|squads, mobile. History is only used within the same class (checkbox `approx` allows nearby classes explicitly), and the same format (game count + scoring). Same-region events come first and carry the most weight; other regions of the same gamemode and format are added only when the region has fewer than `model.MIN_SAME_REGION` (4) previous events (`model.comparable`, `strategy.peers`, strategy `_refs`).
- Live: player-by-player simulation (`sim.py`) using comparable players at the same moment in same-class past events (games played, points/game, pace scaling), with back-test bias correction. Ranks >700 scale from rank 500; ranks never predicted below current.
- No history for a class = explicit "no history" message.

## Strategy layer (added Oct 2026)
- `strategy.py` feeds the Strategy tab: `/api/scoring`, `/profile` (finisher bands, per-game sequences, styles), `/pace`, `/safety`, `/ladder`, `/tempo` (minutes per game by placement from consecutive game end times; a stored game time is the player's elimination time); `me.py` looks a player up by Epic name on the public leaderboard (`/api/me`, `/api/account`); `service.sessions` (`/api/sessions`) lists the rounds/editions of an event in a region; `/api/calendar.ics`, `/api/feedback` (owner reads with the admin key), `/api/health` (banner).
- Front end: `lib.js` (helpers, Chart.js theme, zoom/click wiring), `strategy.js` (recommendation, plan, simulation, coach notes), `app.js` (pages, router, account chip, banner). Charts use `mk()`; animations are off on purpose (Chart.js errors when a click redraws a chart).
- Timing facts that drive the plan: games left = format games minus games played; games that fit = time left / minutes per game at your placement (a game may start right before the window closes). Finishers' points fall with game number, so checkpoints and the simulation follow real sequences, not an even split.
- Tests: `python -m unittest discover -s tests`.

## Operations lessons
- **Never run local code that uses the production Epic login** (`auth.Session`, `/api/me`, `/api/account`, the collector). The refresh token rotates on every use; the live login died on Oct 14 2026 while local tests were also using it (cause not proven). Local test servers must stub `auth.Session` (see how `serve.py` in a scratch folder does it) and intercept `/api/me` in browser tests. Re-login (Status page) is the only fix and needs the owner's Epic authorization code.
- `auth_bad` in kv marks a refused login; `auth.bearer` then waits 10 minutes before calling Epic again. The site shows a banner when the collector has not run for 15 minutes or the login is invalid.
- Do not read other players' Epic data by account id: Epic returns 403 for anything but your own account; the public leaderboard (`Epic.find_entry`) is the only way.

## Roadmap ideas not built
- Real gameplay telemetry (landing spots, rotations, fights): Osirion's public API or replay parsing. Needs a terms check first; plan-aware drop advice ("which drop fits your target rank, time and style") is the differentiator.
- Clock-time advice ("when to queue") was tested and rejected: later games score more only because deep runs end later, so survival and clock time cannot be separated.

## Dropspots (landing data)
- Tab `#/drops[/window]` (`web/drops.js`, `drops.py`, `/api/drops/*`): heatmaps of where teams landed (qualified = final rank within the top N, versus everyone), a game filter, drawn areas (box, freehand, named spot) with the stats of the teams that landed there, and a comparison table of named spots. It also states which playlist/map an event uses (Epic's event data only gives the playlist id).
- **The leaderboard has no landing data; the replays do.** Epic keeps a server replay of every tournament match for about 1-2 weeks, keyed by the `sessionId` that each leaderboard entry lists per game (same id Osirion/Fortnite Tracker show as match id). Rows go in with `POST /api/admin/drops` (format in `docs/dropspots-data.md`); tables `drops` and `drop_maps`.
- **Replay pipeline (no paid service):** `GET /api/admin/matches?window=` lists every session of a window with its teams, rank, game number, placement, elims, points (`replays.matches`); `GET /api/admin/replay?session=&max_ms=` returns the file list and 15-minute signed links (`replays.links`; metadata at `/api/v1/data/fnreplaysmetadata/public/<id>.json`, links by POSTing `{files:[...]}` to `/api/v1/access/fnreplays/public/<id>/`; the site's own login works). `worker/replay.mjs` downloads the header and only the first data chunks (landings happen in the first minutes; ~8 MB instead of 43) and assembles a `.replay`; `worker/landings` (C#, net10, references Shiqan/FortniteReplayDecompressor, GPL-3.0, pinned commit 76f74c1, pure C# Oodle) prints each player's landing = first moment after leaving the bus with vertical velocity exactly 0, plus a ground trail; `worker/run.mjs <window>` ties it together (samples matches: half the ones with most qualifiers, half random; teams matched to the leaderboard by account ids; north-up map: u = Y, v = -X; posts rows, a background map drawn from player movement `map.base`, and `sessions_done` so reruns skip finished matches). `.github/workflows/drops.yml` runs it every 3 hours on GitHub Actions and needs the repo secret `ADMIN_KEY`.
- The map background is drawn from where players moved (no outside image, no copyright question); bounds default to +-55000 world units (`MAP_BOUNDS`). Named spots are not available (Epic ships no POI table in the replay): only drawn areas.
- **Map picture** (`drops.MAPS`, `web/maps/`): registered per playlist codename (`SourSpawn` = Nitemare Island, found by fitting wiki overview images to the landings and by names inside the replay, see `tools/mapfit/`). The picture is rotated/scaled into the site's 0-1 frame and ships with a land/water outline (`*.mask.json`); `drops.picture_check` tests the real landings against it and hides the picture when under 93% are on land (`map_check` in `/api/drops/info`). A new codename has no picture until someone identifies it (draws the background from player movement meanwhile).
- **Chests and loot** (`/api/drops/loot`, `/areas`, `_sites`): the replay has no chest objects (UEFN maps), but a chest opened by a player spits out 5+ pickups at one spot within 0.6 s. The landing tool (`Spy` in `worker/landings/Program.cs`) finds those bursts after 40 s of replay time, **removes player-death drops** (burst within 600 uu and 4 s of a player's DeathLocation/DeathTime, using the game-clock offset taken from PlayerPawn timestamps) and anything over 9 items; the worker counts per 360x360 map cell the matches that had a burst and the server (kv `chests:<codename>`, shared by every event on that map) turns peaks seen in at least 5% of matches into chest sites. **Lootage rate** = share of matches in which that chest was opened in the first minutes (about 3 min of game, the downloaded part). Areas = greedy clusters of sites (radius 0.055) with chests, lootage, average players per game (landings share x teams per match x team size, counted from every team in the replay, not only the leaderboard), loot score = chests / (players + 1), chests per player and chests still free. Needs 20 processed matches of a map.
- Teams not on the stored leaderboard (rank beyond 10,000) are still loaded: game number 0 (only in "All games"), rank 0, points from the replay's elims.
- Predictions: `service._run_predict` accepts any top 1-10,000; ranks 701-1000 read the stored top-1000 boards of same-format events, ranks above 1000 interpolate the stored thresholds; a field-size check says plainly when a rank is outside what events of that format had (small finals have 17-20 teams).
- Operations: the replay endpoints use the production Epic login only for small requests (never run the collector or `auth.Session` locally; the worker only talks to the site). Auto-mode classifier on the dev machine often blocks these commands; they succeed right after the user says "run".
